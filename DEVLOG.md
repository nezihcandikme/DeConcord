# DEConcord Devlog

The README tells you what DEConcord is. This tells you why it looks the way it does: the actual decisions, the bugs that forced them, and the things I considered and didn't do. Git commit messages say *what* changed. This is for the *why*, in more than one line.

*(This project was called BioInsight through Aug 13, then OmicForge through Aug 14, then DEConcord from Aug 14 onward. Entries written before each rename refer to the project by whatever name it actually had at the time. That was accurate when written and hasn't been changed.)*

Organized by day, not by session. A day can have several working sessions in it, but each entry below is one consolidated record of what changed and why, not a session-by-session transcript. Early entries are shorter because they're reconstructed from the commits and the code itself. I didn't start keeping a real devlog until Aug 11, so I'm not going to pretend I remember internal debates from Aug 6 that I didn't write down.

---

## Aug 6: the CSV era

Started with the most mundane problem in the whole pipeline: is this CSV even a valid count matrix. Built an exception hierarchy (`CountMatrixError` and specific subclasses for non-integer, negative, duplicate-index, and missing-value cases) instead of one generic error. "Your data is bad" is useless. "Column X has negative values" is actionable.

Decision worth naming: `validate_counts` collects *every* problem it finds and raises them together, instead of stopping at the first one. Nobody wants to fix one validation error, rerun, hit the next one, and rerun again. Better to get the whole list at once.

## Aug 7: the data has entered the building

Added `load_count_matrix` (read CSV, validate, done), then the first QC metrics: library size and genes detected per sample. Outlier detection used MAD (median absolute deviation) instead of standard deviation. The point is catching a sample that's wildly different from the rest, and a couple of extreme samples will drag a mean and standard deviation right along with them, hiding themselves in the process. MAD doesn't have that problem.

CPM normalization also went in this day. This is the first place "sample A got sequenced deeper than sample B" stopped being a caveat and became something the code actually had to correct for.

## Aug 8: statistics have consequences

Added log2(x + 1) transformation, then the first differential expression code: a mean-difference "log fold change" and a per-gene Welch's t-test. Welch's over the standard Student's t-test because there's no good reason to assume both groups have equal variance, and RNA-seq expression variance is routinely condition-dependent. Assuming equal variance would have been the wrong default, not just a simplifying one.

This is roughly where "the code runs" stopped being the bar and "does this number mean what I think it means" took over. It would keep not being enough for a while.

## Aug 9: thousands of p-values appeared

Added Benjamini-Hochberg correction, a minimum-sample-size check for the t-test, volcano and PCA plots, and hypergeometric pathway enrichment. This is the day BioInsight stopped being "the CSV thing" and became an actual small pipeline with an end product.

## Aug 11: make it harder to fool, then make it honest about what it is

The longest day so far, by a wide margin. Grouped by topic below, not by sitting, since the topics are what matter a year from now, not the session breakdown.

**Correctness pass (v0.3.1).** A full walk through the whole pipeline looking for the gap between "the code doesn't crash" and "the code is right." Found more than expected:

- Every `__init__.py` in the project except one was misspelled (`_init_.py`, `__init_.py`, even `__init.py`), and the top-level `bioinsight/__init__.py` didn't exist at all. Python's namespace-package fallback was quietly papering over this. Exactly the kind of thing that works until it doesn't. Fixed all of them.
- Pathway enrichment wasn't restricting to the tested background before computing overlaps, so a gene that was never even eligible to be "significant" could still inflate the enrichment p-value. Fixed by intersecting `significant_genes` and each `gene_set` with `background_genes` before touching the hypergeometric math.
- `compute_cpm` divided by zero silently for any sample with zero total counts. Now it raises, and names the sample.
- Constant-expression genes produced NaN p-values, since Welch's t-test is undefined when both groups have zero variance. Special-cased it: identical constants means "not different" (p=1), differing constants means "as different as it gets" (p=0).
- A duplicate test function name in `test_pathway_analysis.py` had Python silently letting the second definition shadow the first, so half the intended coverage was never actually running.
- Wrote `bioinsight.pipeline.run_analysis()` so the modules could be run as one call instead of manually chained every time.

**Humanizing the docs surfaced more bugs (v0.3.2).** Rewriting docstrings to actually sound like someone who understands the function wrote them forced a close enough re-read to find real problems, not just prose ones:

- `compute_adjusted_pvalues` silently turned *every* adjusted p-value in the whole batch to NaN if even one input p-value was NaN, a `statsmodels` quirk. Now it checks and raises, naming the offending gene.
- Same function crashed outright (`ZeroDivisionError`) on an empty p-value Series. Found while writing a test for "what if `run_pathway_enrichment_analysis` gets an empty `gene_sets` dict," a real edge case, not a hypothetical one.
- `plot_pca` handed you scikit-learn's fairly cryptic error below 2 samples or genes. Added a guard that says what's actually wrong.
- `plot_volcano` could plot `-log10(0) = -inf` for a gene with an exact-zero adjusted p-value, newly possible once the constant-expression fix above started returning literal 0.0. Floored it before plotting.
- `validate_counts` now warns (doesn't fail, it's a heuristic) if a matrix looks like it might be transposed.
- Pathway enrichment's result columns were `'Pathway'`, `'P-value'`, etc. (Title Case), while DE results use snake_case. Renamed the pathway columns to match. A deliberate breaking change, made while nothing outside this repo depended on the old names yet.
- DE functions now reject missing sample names, a sample listed twice in one group, and a sample appearing in both groups. Each error names the actual sample, instead of a bare pandas `KeyError` or a silently nonsensical comparison.

**Configurable significance thresholds (v0.3.3).** `adjusted_p_value < 0.05` and `abs(log_fold_change) > 1` were hardcoded into `run_differential_expression`. Neither number is statistically special, they're conventions, so baking them in meant anyone who disagreed had to edit the source. Added `alpha` and `lfc_threshold` as real parameters (same defaults, validated on the way in), threaded through `run_analysis` too.

**Pre-DE low-count filtering (v0.4.0).** Added `bioinsight.filtering.filter_low_count_genes(df, min_count=10, min_samples=2)`. Every gene handed to `compute_pvalues` gets tested, and every test tightens the Benjamini-Hochberg correction for every *other* gene, so a gene that was one read away from zero everywhere was only ever going to be dead weight. Wired into `run_analysis` as opt-in (`min_count=None` by default). The function itself always filters when called directly, but defaulting the *pipeline* to filter would have silently changed which genes get a p-value for every existing caller. QC still runs on the raw, unfiltered matrix first, so filtering can't skew a sample's own quality numbers.

**Splitting the docs: README as the pitch, this file as the record.** The README had grown into something that tried to be a landing page, an install guide, an API reference, and a statistics disclaimer at once. Readable, but not *explanatory* the way a first-time visitor needs. Stripped it down to what BioInsight is, why it exists, and where it's headed. Moved every code block, module table, and exact threshold out. This file exists so none of that reasoning actually gets lost. It just moved.

**The website (`docs/`, GitHub Pages).** Built a static site: plain HTML/CSS and a little vanilla JS, deliberately, because GitHub Pages needs zero build step and the site shouldn't need a toolchain the rest of the project doesn't have. Design direction was Apple x scientific software x developer tool: black/white/gray, one accent color, system fonts, no gradients or icon clutter. The volcano and PCA images on the site are genuine output, generated by calling BioInsight's own `plot_volcano`/`plot_pca` on a synthetic 4,000-gene dataset, with only the color palette adjusted for the marketing image (the library's actual plotting code wasn't touched). Every claim and number on the page traces back to the README or this file. Nothing on the site exists that isn't true of the code.

**GMT gene-set loading (v0.5.0).** Pathway enrichment took `gene_sets` as a plain Python `dict[str, set[str]]`, which meant translating an actual MSigDB or Enrichr download into Python by hand before you could use it. Added `bioinsight.pathway_analysis.gmt.load_gmt(path)`, a thin parser for the standard tab-separated GMT format (name, description, then genes), returning exactly the dict shape `run_pathway_enrichment_analysis` already expects. Kept it in its own file instead of `methods.py`, since parsing a file format and running a statistical test are different jobs that don't need to share a module just because they're both "pathway analysis." Rejects malformed lines, duplicate gene set names, and empty files by name and line number instead of producing a dict that's quietly missing or merging gene sets.

## Aug 12: a CLI, and cleaning up after myself

**Command-line entry point (v0.6.0).** Every single use of BioInsight so far meant writing a Python script that imports `run_analysis` and calls it. Fine for me, annoying for literally anyone else who just wants to point the pipeline at a CSV and get results back. Added `bioinsight/cli.py`, an argparse wrapper around `run_analysis`, wired up as a real console script (`[project.scripts]` in `pyproject.toml`), so `pip install`-ing the package gives you a `bioinsight` command, not just an importable package.

It's deliberately thin: no logic of its own beyond argument parsing and writing outputs to disk (DE table and QC table as CSV, plots as PNG, pathway enrichment as CSV if a `--gmt` file was given, an explanation as a text file if `--explain` was passed). All the actual pipeline logic still lives in `run_analysis`. The CLI's only real design decision was what to do about a background gene universe for enrichment when the user doesn't hand-specify one with `--background`. It defaults to every gene in the input matrix, the same "everything that could have been tested" reasoning the library docstring already commits to elsewhere, just applied automatically instead of requiring the caller to know to do it.

Errors a user is likely to actually hit, a missing file, an unknown sample name, a malformed GMT line, get caught and printed as a one-line `bioinsight: ...` message with exit code 1, instead of a Python traceback. Anything outside that expected set of exceptions is left to crash loudly, on purpose. A CLI that swallows every exception into a generic "something went wrong" is worse than one that occasionally shows you a traceback for a real bug.

Tested it two ways: a normal pytest suite (`tests/test_cli.py`, 7 tests, happy path, `--no-plots`, `--gmt`, `--min-count` filtering, and three failure modes) calling `main()` directly, then actually installing the package into a clean venv and running the real `bioinsight` command against a real CSV. A CLI's argument parser and entry-point wiring are exactly the kind of thing that can pass every unit test and still be broken the moment a real shell invokes it.

**Also found and removed two committed accidents.** `test_pca.png` and `test_volcano.png` had been sitting at the repo root since the very first plotting commit (Aug 9, v0.2), leftover output from manually eyeballing a plot locally, never meant to be tracked. Removed them and added `/test_*.png` and `/bioinsight_output/` (the CLI's default output folder) to `.gitignore` so it doesn't happen again, either by hand or by running the new CLI inside the repo.

**Site refresh.** Version bump aside, regenerated the volcano and PCA demo images on `docs/` by actually running the new `bioinsight` CLI against a fresh synthetic dataset, in-process, and copying its real output PNGs straight onto the site. More honest than the previous approach of calling the plotting functions directly, since it's now the exact same code path a real user's terminal would hit. The old demo happened to land on 207 significant genes; this run landed on 515 out of 4,000 with a different random seed's worth of synthetic effect sizes. Both numbers are real, neither is picked to look good, and the hero terminal panel and capabilities grid (now 10 items, laid out 5x2) got updated to match: a CLI card, a GMT-loading card, and the hero code block now leads with the actual `bioinsight ...` command and its real stdout instead of a Python-only example.

**Simplifying the site.** Went back through `docs/` and cut the one piece of the design that didn't earn its place: a scroll-triggered fade-up animation on every section (an `IntersectionObserver` in `script.js` plus matching CSS). It looked fine, but it's exactly the kind of thing that reads as "trying too hard" on a page whose whole pitch is restraint. Content should just be there when you land on it, not perform an entrance. **Started the DESeq2/edgeR benchmark harness.** The README has said since the docs split that the near-term plan is "check the current results against DESeq2 and edgeR on a real public dataset." Everything else in this project has been building toward being able to say that honestly, so it was time to actually do it. Sandbox reality check first: this environment has no root, no `apt`/`conda`, and network access restricted to `pypi.org` and `github.com`. R, CRAN, and Bioconductor are all unreachable from here. Rather than fake it with a lighter substitute, the plan became running the actual R-based comparison locally instead, so I built the harness for that: `benchmarks/run_deseq2_edger.R` pulls the `airway` dataset (the same one DESeq2's own vignette uses: 8 human airway smooth muscle samples, 4 cell lines, untreated vs. dexamethasone-treated), runs DESeq2 and edgeR with each package's own standard, untuned workflow, and writes out both their results and the raw input matrix. `benchmarks/compare_results.py` then runs BioInsight on the identical matrix and groups and reports log fold change correlation and significant-gene overlap against each tool, plus scatter plots.

One sign-convention bug worth naming so it doesn't bite again: `compute_log_fold_change` returns `mean(group_1) - mean(group_2)`, so getting `group_1`/`group_2` backwards relative to DESeq2's `contrast=c("dex","trt","untrt")` would silently flip every correlation negative. Not a code bug, just an easy way to misread real results as a disagreement that isn't there. Documented directly in the comparison script's own comments instead of leaving it as a trap.

Smoke-tested `compare_results.py` end to end against fabricated mock CSVs shaped like real DESeq2/edgeR output (never committed, deleted immediately after) to catch parsing and column-name bugs before handing this off. The real run, with real R installed, is next. Whatever those numbers turn out to be, favorable or not, they get written up here as-run.

**The real run.** Results are in `benchmarks/results/` (`comparison_summary.md`, `lfc_vs_deseq2.png`, `lfc_vs_edger.png`). The actual numbers, on the real `airway` dataset, real DESeq2 and real edgeR, both run with their own default settings:

- **Fold change direction and magnitude track well.** Pearson r = 0.938 against DESeq2, 0.947 against edgeR. Spearman rho = 0.982 / 0.983. The two methods are looking at the same underlying signal and mostly agree on how big it is.
- **Precision is 1.0 against both.** Every single gene BioInsight calls significant (196 of them, out of 16,139 tested after `min_count=10` filtering), DESeq2 and edgeR also call significant. Zero disagreement in that direction. Nothing BioInsight flags turns out to be a false alarm relative to either reference tool.
- **Recall is low: 0.075 against DESeq2 (2,618 significant), 0.098 against edgeR (1,990 significant).** BioInsight finds under a tenth of what the count-based tools find. This is the real, quantified cost of testing each gene in isolation with a t-test instead of a negative-binomial GLM that borrows statistical power across genes with similar expression levels (via empirical Bayes dispersion shrinkage), exactly the mechanism `benchmarks/README.md` predicted would cause this gap, before the run happened.
- **One more thing the scatter plots show that wasn't predicted going in.** For the genes with the largest observed differences (DESeq2/edgeR log2FC of 5 to 10), BioInsight's estimate systematically undershoots theirs. Points bend below the y=x line on the positive side, above it on the negative side. Most likely explanation: `results()` without `lfcShrink()` returns DESeq2's unshrunken MLE, which can produce very large coefficients for genes with near-zero counts in one group. This is precisely why DESeq2's own docs recommend `lfcShrink()` for reporting effect sizes rather than raw `results()` output. BioInsight's `log2(CPM + 1)` transform bounds this by construction: a pseudocount limits how large a ratio involving a near-zero count can get. Not claiming BioInsight is "more correct" here, just noting where and plausibly why the two disagree most.

So: the thing the README said BioInsight hadn't done yet, check it against the field's actual tools instead of describing itself as "not validated" and leaving it there, is done, on one real dataset. The honest one-line summary is precision 1.0, recall about 0.08 to 0.10 against DESeq2/edgeR defaults: when BioInsight finds something, it's very likely real. It just doesn't find most of what's there. That's a specific, falsifiable claim now, not a vague disclaimer.

## Aug 13: closing the loop the benchmark opened

Yesterday's benchmark measured a real weakness instead of just gesturing at one: recall of 0.075 to 0.098 against DESeq2/edgeR, because a per-gene t-test has nothing to fall back on when a gene's own replicates happen to be noisy. Today's the direct response to that specific number.

**Empirical Bayes moderated t-test (v0.7.0).** Added `compute_moderated_pvalues` alongside the existing `compute_pvalues`, selectable via a new `method` parameter (`"welch"`, still the default, or `"moderated"`) threaded through `run_differential_expression`, `run_analysis`, and the CLI's new `--method` flag. The idea, the same one behind limma's `eBayes`/`squeezeVar` (Smyth, 2004), is to stop trusting each gene's own variance estimate in isolation and instead shrink it toward a value fit from every other gene's variance. A gene with a real effect but one noisy replicate no longer has to fight its own bad luck alone.

Implementation is a method-of-moments fit of the prior (`d0`, `s0-squared`) using the trigamma function (`scipy.special.polygamma(1, ...)`) on the log of per-gene pooled variances. Same math limma's `fitFDist` is built on, simplified to a direct solve (`scipy.optimize.brentq`) rather than an iterative MLE, and assuming every gene shares the same residual degrees of freedom (true here, since BioInsight's design is always a fixed two-group comparison). Documented plainly as a real, honest tradeoff, not a strictly better upgrade: the pooled-variance model this needs assumes a gene's two groups share one variance, which is exactly the assumption Welch's t-test was chosen back on Aug 8 to avoid. More power, different assumption, not "the fixed version" of the old one.

A side benefit that fell out of the math rather than being designed in: because the shrinkage prior is never exactly zero, a constant-expression gene no longer needs `compute_pvalues`'s ad hoc zero-variance special case (`p=1` if means match, `p=0` if they don't). It gets a well-defined, usually large but finite p-value automatically, straight from the same formula every other gene uses.

**Tested the actual power claim, not just that the code runs.** The one test that matters most here (`test_compute_moderated_pvalues_shrinkage_beats_unmoderated_for_noisy_gene`) builds 24 tightly-clustered background genes plus one gene with a real mean difference and one wildly noisy replicate, then asserts the moderated p-value for that noisy gene beats a plain pooled t-test computed on its own variance alone. This proves the shrinkage does what it's supposed to, not just that it produces *a* number.

**Reran yesterday's exact benchmark with the new method.** Same real `airway` data, same real DESeq2/edgeR output already on disk, no need to touch R again. Result:

- Significant genes: 196 to 431 (more than double).
- Recall vs. DESeq2: 0.075 to 0.165. Recall vs. edgeR: 0.098 to 0.217.
- Precision: still exactly 1.0 against both. More than double the discoveries, zero new false alarms relative to either reference tool.

Fold change correlation barely moved (0.938 to 0.938 vs. DESeq2, 0.947 to 0.947 vs. edgeR), expected, since moderation only changes the variance/significance side of the test, not the mean-difference estimate. `benchmarks/compare_results.py` now takes a `--method` flag and writes suffixed output (`comparison_summary_moderated.md`, `lfc_vs_deseq2_moderated.png`, etc.) so the welch run's committed results stay untouched and both are on record.

**Gene ID to symbol annotation (v0.8.0).** Real motivation, not a hypothetical one: the actual `airway` benchmark output is indexed by Ensembl IDs (`ENSG00000141510` and so on), correct, but nobody reads a results table like that comfortably. Added `bioinsight/annotation/` (`load_gene_annotation`, `annotate_de_results`), following the exact precedent `pathway_analysis/gmt.py` set: no live Ensembl/BioMart/API call, just a local two-column CSV (`gene_id,gene_symbol`) you already have or exported once. Wired into `run_analysis` (`gene_annotation`, accepting either a path or an already-loaded dict, same path-or-object pattern `counts` already uses) and the CLI (`--annotation`).

The one real design call: unmapped genes get `gene_symbol = NaN`, not a fallback to the gene ID. Falling back was tempting, never an empty-looking cell, but it would make "genuinely unmapped" indistinguishable from "the symbol happens to equal the ID," which is a worse failure mode than an honest blank. The original ID stays exactly where it always was, as the index. The symbol is purely additive.

Validation follows the same loud-by-default pattern as the rest of the input-loading code: missing columns, a header with zero data rows, a row missing either value, and, the one most worth catching, the same gene ID mapping to two *different* symbols in different rows, which raises naming the ID rather than silently keeping whichever row happened to load last.

**The real `pasilla` run.** Results in `benchmarks/results/` (`comparison_summary_pasilla.md`, `lfc_vs_deseq2_pasilla.png`, `lfc_vs_edger_pasilla.png`):

- **Precision is 1.0 against both**, same as `airway`. Every one of the 71 genes BioInsight (welch) calls significant, out of 7,920 tested after `min_count=10` filtering, DESeq2 and edgeR also call significant.

That consistency is the actual finding here, more than either number on its own: "zero false alarms, finds roughly a tenth of what count-based tools find" isn't a quirk of one dataset's noise structure or one lab's sequencing depth. It held up, within a couple of percentage points, on a second species with a completely different design. That's a meaningfully stronger claim to make about the welch method's behavior than one dataset alone could support.

*GEO acquisition (`bioinsight/io/geo.py`).* Scoped deliberately narrow: lists and downloads a GEO series' submitter-uploaded supplementary files, and parses the series matrix file's own `!Sample_characteristics_ch1` lines into a metadata DataFrame. The tedious, uniform part (finding NCBI's FTP bucket path, listing what's there, parsing that specific text format). It does not touch raw SRA/FASTQ data or try to guess how to turn an arbitrary submitter's file into a clean count matrix, since neither is uniform enough across GEO series to solve generically without overpromising. The `nextflow-development` skill already covers the FASTQ-to-counts case properly. Same network caveat and same mocked-`urlopen` testing approach as the g:Profiler client.

Worth writing down what got *rejected*, not just what shipped:

- **Silently supporting both old and new pathway column names**, instead of a clean breaking rename. Would have avoided the breaking change, but permanently: every future reader would have to know two names meant the same thing for no active reason. Rejected.
- **Validating matrix orientation as a hard error** instead of a warning. There's no way to be *certain* a wide, short matrix is transposed rather than just a small custom gene panel. It's a heuristic, and heuristics that hard-fail on a guess are worse than ones that speak up and let you decide.
- **Assigning an arbitrary small p-value (like 1e-10) instead of exactly 0.0** for constant-expression genes with a clear between-group difference. Went with exactly 0.0 because it's honest about what the test is actually saying ("as significant as this method can express"), and handled the downstream consequence (the volcano plot's `-log10(0)`) directly instead of avoiding it by fudging the number.
- **Reimplementing edgeR's `filterByExpr`** (which accounts for group sizes and normalized CPM, not just a flat raw-count cutoff) instead of a simple fixed threshold. `filterByExpr` is the more defensible method, but it's also a meaningfully bigger piece of statistical machinery to get right and test. Shipped the simple version now. The module docstring says outright that it isn't `filterByExpr`, so nobody mistakes "good enough to stop testing dead genes" for "the field-standard algorithm."
- **Duplicating install/usage commands in both the README and this file**, for convenience. Rejected. Two copies of the same command drift the moment one changes and nobody updates the other. The README has the one copy that matters for actually running the thing.
- **A separate repo for the website** (e.g. a dedicated site repo, or the classic `username.github.io` pattern). Rejected in favor of `docs/` inside this repo: one source of truth, and a design/content update to the site can't quietly fall out of sync with the code it's describing.
- **`click` or `typer` instead of `argparse`** for the CLI. Both are nicer to write. Neither is worth a new dependency for a handful of flags that the standard library already handles fine. `argparse` stays until the CLI's surface area actually outgrows it.
- **Making `"moderated"` the new default DE method**, instead of `"welch"`. It found more than double the significant genes on the real benchmark with zero extra false alarms, a tempting case for making it the default. Rejected anyway: it's a different statistical model with a different assumption (shared variance per gene across groups), not a strict upgrade, and switching the default would silently change every existing caller's results out from under them the moment they upgraded. Opt-in via `method="moderated"`, same pattern as `min_count` filtering.
- **Falling back to the gene ID when a symbol is unmapped**, instead of `NaN`, so annotated tables never show a "blank" cell. Rejected. It would make an actually-unmapped gene look identical to a gene whose real symbol happens to equal its ID, which is strictly worse than an honest missing value. `NaN` is also just easier to filter on (`df["gene_symbol"].isna()`) than a column mixing real symbols with IDs pretending to be symbols.
- **Fetching annotation live from Ensembl/BioMart/MyGene.info** instead of a local file. Would be more convenient when it works, but adds a network dependency this project has otherwise deliberately avoided (the only other outbound call is the opt-in AI explanation layer), and the sandbox this gets built in can't reach any of those hosts anyway. Same reasoning that shaped the GMT loader.
- **Enrichr instead of (or alongside) g:Profiler** for live enrichment. Enrichr's API is a two-step add-list-then-fetch flow rather than a single request/response call, which is a meaningfully bigger client to write and test for a first pass at "does live enrichment integration make sense here at all." g:Profiler covers the same core need (GO/KEGG/Reactome, no API key) in one endpoint. Not ruled out permanently, just not worth the extra surface area for a v1.
- **Making `run_analysis` fetch data straight from a GEO accession**, instead of keeping `bioinsight.io.geo` a separate, manually-invoked step. GEO submitters don't upload a uniform format: sometimes a clean count matrix, sometimes per-sample files, sometimes something else entirely. Silently guessing how to turn a downloaded file into `counts` would be exactly the kind of "convincing nonsense" this project's whole premise is about avoiding. Left the judgment call with the caller.
- **Building any raw SRA/FASTQ handling into this project**, as part of "GEO/SRA data acquisition." Turning reads into counts means alignment and quantification, a genuinely different, heavier job, and one this project's own environment already has a dedicated tool for (an nf-core/rnaseq-based skill). Scope stayed at "help get from a GEO accession to a count matrix a submitter already made," not "replace an alignment pipeline."

**Covariate-adjusted differential expression (v0.11.0).** The two-group test, Welch's or moderated, has always treated every sample outside group_1/group_2 membership as irrelevant. That's fine until a real confound shows up: a batch, a sex difference, an extraction date, anything that happens to correlate with which samples ended up in which group. In that case the group_1-vs-group_2 mean difference isn't measuring the condition anymore, it's measuring the condition tangled up with whatever else varies alongside it.

Added `run_differential_expression_with_covariates` to `differential_expression/methods.py`: a per-gene linear model, `expression ~ intercept + condition + covariates`, fit by OLS across every gene at once (one design matrix, `X.T @ X` inverted once, `beta = (X'X)^-1 X'Y` vectorized over all genes as columns of `Y`) rather than looping a per-gene `statsmodels.OLS` call. Same result, meaningfully faster for anything past a toy dataset. The condition coefficient is what gets tested. Everything else is along for the ride only to keep it honest. Categorical covariates get one-hot encoded (first level alphabetically dropped as reference); numeric ones go in as-is, on the explicit assumption that their effect is linear, which is a real assumption and not automatically checked. There's deliberately no Welch's-test equivalent here. Welch's test is specifically a two-independent-samples comparison and doesn't generalize to "compare two levels while holding a third variable fixed." A linear model is what that actually requires. Variance moderation reuses `_fit_ebayes_prior` completely unchanged. It was already parameterized on an arbitrary `df_resid`, so the same empirical-Bayes shrinkage that helps the plain two-group moderated test generalizes to any design matrix for free, no new math needed.

Wired into `run_analysis` as `metadata`/`covariate_cols`/`moderated_covariates`, and the CLI as `--metadata`/`--covariates`/`--no-moderated-covariates`. Deliberately reused the existing `group_1`/`group_2` naming instead of inventing a `condition_col`/`level_1`/`level_2` vocabulary. The covariate path is still "compare these two sample lists," just with extra terms in the model, and the sign convention for `log_fold_change` (group_1 relative to group_2) stays the same as everywhere else in the codebase.

Caught one real design gap while writing the tests: a single-level categorical covariate (every sample the same batch) produces *zero* one-hot columns once the reference level is dropped. `pd.get_dummies` doesn't error, it just silently contributes nothing to the design matrix. Without an explicit check, that covariate would vanish from the model with no warning at all, which is a worse failure mode than the rank-deficiency error a numeric constant covariate correctly triggers (a constant number collides with the intercept column and gets caught by the rank check). Added a direct check for zero-dummy-columns with its own message, since the two failure modes look identical to a user ("I gave it a covariate and something's wrong") but need different explanations.

Verified the confound scenario is real, not just plausible-sounding: a synthetic gene with a true condition effect of +2.0 and a batch effect of +5.0, where batch is unevenly split across the two condition groups (2-of-3 vs. 1-of-3), gives a naive `compute_log_fold_change` of about 0.33. The batch effect nearly cancels the condition signal out. `run_differential_expression_with_covariates` on the same data recovers about 2.0, matching an independent from-scratch `numpy.linalg.lstsq` solve of the same design matrix built separately in the test.

Test count: 145 to 167.

Decisions rejected along the way:

- **A `formula`-string interface** (`"~ condition + batch"`, patsy-style) instead of explicit `group_1`/`group_2`/`covariate_cols` arguments. More flexible eventually, but it's a new dependency (`patsy` or a hand-rolled formula parser) and a new syntax to document for a feature that, right now, only needs "two groups plus some covariate columns." The existing `group_1`/`group_2` vocabulary already does the condition part. Adding a formula parser on top would be solving a problem this project doesn't have yet.
- **Supporting more than two condition levels** (e.g. a three-way tissue comparison) in the same function. That's a real, different feature: multiple pairwise contrasts or an ANOVA-style omnibus test, not just "one more covariate." Mixing it into this pass would have made the design matrix logic (and its error messages) noticeably harder to get right. Left for later, noted in the README roadmap.
- **Silently dropping a covariate that turns out to be redundant** (perfectly correlated with condition, or with only one level) rather than raising. Would make more datasets "just work," but the whole reason to adjust for a covariate is that it's supposed to be doing something in the model. A covariate that silently contributes nothing is a sign the input is wrong, not something to paper over.
- **A plain, unmoderated OLS-only implementation**, dropping the `moderated` option to keep the function simpler. Kept both because the plain two-group test already offers the same choice (`method="welch"` vs `"moderated"`), and small experiments are exactly where a handful of genes plus a few covariates leaves too little residual-df to trust an unshrunk per-gene variance estimate. The moderated path is where this feature is most useful, not an afterthought.

## Aug 14: narrowing to one question, and renaming to DEConcord

Looked up OmicVerse (Zeng et al., *Nature Communications* 2024) after wondering out loud whether it already did what this project was reaching for. It does, and then some: bulk, single-cell, and spatial transcriptomics under one API, synthetic biology and molecular dynamics modules, an AI-agent/MCP layer. Published, actively maintained, built on top of roughly fifty other published tools (PyDESeq2 and edgeR among them) rather than reimplementing their statistics. That last part is the actual distinction that matters, not the feature count: OmicVerse wraps established tools so you don't have to look inside them. This project's entire reason for existing was looking inside them. Every DE method here (Welch's, moderated, covariate-adjusted) was written from scratch specifically to understand the mechanics, not to ship a faster way to get a p-value. Those aren't competitors. But "grow toward a broader omics platform," which the README's own roadmap had been drifting toward, was competing with something that already won that race with a two-year head start and a paper behind it. Continuing to add scope in that direction would have made this a permanently smaller, permanently behind copy of a thing that already exists and is better at being that thing.

So: narrower, not broader. The question that's actually interesting, and that a small project can actually own, isn't "can this analyze more kinds of data." It's "how much do the conclusions from an RNA-seq DE analysis actually depend on which reasonable choice you made along the way." Two independent, competently-run tools (DESeq2, edgeR) on the same count matrix don't automatically agree, and by how much they agree or disagree is itself real information: about the data, about which findings are solid, about which ones are one arbitrary choice away from disappearing. Nobody was measuring that number for its own sake. Everyone was busy trying to pick the "right" tool instead. That's the actual gap, and it doesn't require out-building OmicVerse to fill it. It requires being careful about a narrower thing.

**Rename: BioInsight to OmicForge to DEConcord**, in about 24 hours, a faster turnaround than any rename should really need. But the first rename (to OmicForge) was about a name collision and a vaguer "grow toward general omics" ambition, and this one is about actually changing what the project *is*. DEConcord means Differential Expression Concordance, and it's meant literally: the software's job is measuring concordance, not doing the differential expression itself, though it still can, as infrastructure (see below). Same mechanical playbook as the OmicForge rename: `git mv deconcord/`, word-boundary `sed` for the bulk of it, then a manual pass for the handful of underscore-adjacent identifiers `\b` can't reach (`omicforge_output` to `deconcord_output`, `run_omicforge`/`omicforge_significant` in `benchmarks/compare_results.py`). Same rule as before on what doesn't get touched: every DEVLOG entry above this one keeps whatever name was accurate when it was written; the committed benchmark `.md`/`.png` outputs keep saying "OmicForge" too, for the same reason.

**What actually got built, not just renamed.** `deconcord.concordance.methods.compute_de_concordance(results_a, results_b, ...)` takes two DE result tables (any tool, any column names, configurable) and reports significant-gene overlap, Jaccard index, Pearson/Spearman correlation of log fold change across every gene both tables tested, directional agreement (among genes significant in *both*, what fraction agree on the sign of the effect, a number the old `compare_results.py` never actually computed, despite computing almost everything else this function does), and explicit concordant/discordant/method-specific gene lists rather than just their counts, since a future pathway-stability stage needs the actual gene sets, not a summary number. Symmetric by design. Neither input is "the one being validated," unlike the old `compare_results.py::compare()` this partly grew out of, which always treated OmicForge's own output as the fixed reference and the other tool as "other."

Ran it for real against the airway and pasilla DESeq2/edgeR result tables already sitting in `benchmarks/results/` from the earlier benchmark work (new script: `benchmarks/method_concordance.py`), first real output from the new core question, not just a passing test. Both datasets: Jaccard about 0.76 to 0.78 on significant-gene overlap, log2FC Pearson r above 0.998, **zero discordant genes** (every gene both tools call significant, they agree on direction). DESeq2 and edgeR turn out to agree with each other a lot more than either agrees with this project's own simple t-test, which is itself informative: the earlier benchmark's recall gap (DEConcord's welch method finding about 8-10% of what DESeq2/edgeR find) isn't "DE tools disagree in general," it's specifically "a per-gene test without cross-gene variance borrowing loses a lot of power relative to tools that have it." Two different comparisons, two different and now much better-understood gaps.

**What deliberately didn't change.** The whole original pipeline, validation, QC, normalization, the three DE methods, annotation, enrichment (local and live), GEO acquisition, plots, stays exactly as it was, just reframed in the README as infrastructure rather than the identity. None of it was thrown away. `run_analysis` still runs end to end, the CLI still works, all 167 tests plus 11 new ones for `compute_de_concordance` pass. The old `compare_results.py` (DEConcord-vs-DESeq2/edgeR precision/recall) also stays as-is rather than being torn out or forcibly rewritten to use the new function's symmetric framing. It's still answering a real, different, still-useful question about DEConcord's own DE methods, and forcing it to share code with something built around a different premise (no "reference" side) would have made both worse just to reduce a line count.

**What deliberately got left for later, not squeezed into today.** No CLI subcommand for `compute_de_concordance` yet. The current CLI is a single flat command built around "run the pipeline," and wiring in a genuinely different verb ("compare two existing result tables") cleanly deserves a subcommand structure (`deconcord analyze` vs `deconcord concordance`), not a bolted-on flag, and that's a real interface decision to get right rather than rush. Threshold sensitivity, pathway stability, resampling, and any actual new robustness statistic are explicitly the next four items in that order. Method concordance had to exist and be checked against real data first, since every later stage either builds directly on it (threshold sensitivity is the same computation swept across a range of alphas) or needs concordant/discordant gene *sets* as an input (pathway stability). Building all six in one pass would have meant guessing at interfaces for stages 2 through 6 before stage 1 had ever touched real numbers.

Test count: 167 to 178.

Decisions rejected along the way:

- **Reimplementing DESeq2/edgeR in Python**, so DEConcord could generate DE tables to compare on its own instead of requiring the user to already have them. Rejected for the same reason OmicVerse's approach of wrapping instead of reimplementing is the right call for a mature platform, and doubly true for a small one: getting a negative-binomial GLM with proper dispersion estimation *right* is a multi-year project on its own, and getting it subtly wrong would produce a tool that *looks* like it's checking concordance while actually just comparing against its own bugs. DEConcord consumes result tables. It doesn't need to be the thing that produces them.
- **A `formula`/contrast-object abstraction layer** to unify "however DESeq2's contrast() works" with "however edgeR's glmQLFTest works" into one interface, so users wouldn't have to already have run both tools themselves. Rejected as premature. The actual interface that matters right now is "here are two CSVs," which is what real usage (including this project's own benchmarks) already looks like. An abstraction over tools DEConcord doesn't run itself would be guessing at requirements instead of building from an observed one.
- **Refactoring `compare_results.py::compare()` to call `compute_de_concordance` internally**, to avoid two implementations of overlapping math. Considered, rejected for now: `compare()`'s precision/recall framing treats one side as ground truth, which `compute_de_concordance` deliberately doesn't do, and forcing a symmetric function to fake an asymmetric one back out (or vice versa) would make the code that actually needs to change later, once threshold sensitivity exists, harder to reason about than a small, temporary amount of duplication.
- **A single combined "robustness score"** folding Jaccard, directional agreement, and correlation into one number, for a cleaner headline metric. This is explicitly what the user's own brief for this pivot warned against: a composite score invented before the infrastructure (threshold sensitivity, pathway stability, resampling) that would give it statistical meaning is exactly "an arbitrary score for presentation." The three numbers stay separate until there's a defensible reason to combine them.

## Aug 14: professionalization pass (v0.13.0)

The rename to DEConcord fixed *what the project claims to be*. This pass is about whether the repository itself backs that claim up: whether someone landing on it from a GitHub search would trust it enough to try `pip install -e .`. No new analytical capability went in on purpose. The brief was explicit that bigger isn't the goal here. Focused, reproducible, documented, tested, and scientifically careful is.

**Structure.** Moved `deconcord/` to `src/deconcord/` (src-layout) rather than the more aggressive flat-file module merge one draft of the brief suggested (`differential_expression.py`, `concordance.py`, etc. all as single files). The existing subpackage structure (`differential_expression/`, `concordance/`, `qc/`, ...) already reflects real, sensible boundaries. Merging it into fewer, bigger files would have been reorganizing for its own sake, exactly what the brief said not to do, while touching every import across 178 tests, docs, and benchmark scripts for no functional gain. src-layout gets most of "looks like a real Python package" (it's what packaging guides recommend, and it stops `import deconcord` from accidentally working against an uninstalled copy) for a fraction of the risk.

**Public API.** `deconcord/__init__.py` was empty before this pass. `import deconcord` gave you nothing, every call site had to know the exact submodule path (`from deconcord.concordance.methods import compute_de_concordance`). Now it curates the actually-useful surface (`compute_de_concordance`, `run_differential_expression`, `run_analysis`, `load_count_matrix`, the plotting functions, `__version__`) into one `import deconcord as dc` without dragging in `ai_explanation`. That one stays reachable only via its full path, on purpose, so the package stays importable without `anthropic`/`python-dotenv` installed at all.

**Optional dependencies.** `anthropic` and `python-dotenv` were unconditional core dependencies for a feature (`explain_results=True`) that's off by default and used by exactly one module. Moved to a `[project.optional-dependencies] ai = [...]` extra. `pipeline.py`'s lazy import now raises a specific `ImportError` naming `pip install deconcord[ai]` instead of leaking a bare `ModuleNotFoundError` from three stack frames down.

**A real Python 3.9 bug, found by adding the lint step.** `requires-python = ">=3.9"` had been claiming 3.9 support since early on, but the CI matrix only ever tested 3.10 to 3.12, so nobody had actually run this on 3.9 in a long time. Turning on `ruff` (scoped to `E9`/`F`/`FA`, real correctness and version-compatibility issues, not import-sort opinions) caught two PEP 604 union-type annotations (`list[str] | set[str]` in `live_enrichment.py`, `str | None` in `plots.py`) that would raise `TypeError` at import time on 3.9 without `from __future__ import annotations`. Fixed both, added 3.9 back to the CI matrix so this doesn't silently regress again. This is the kind of bug a "looks professional" pass is actually for, not a cosmetic one.

**CLI output layout, a real breaking change, called out rather than hidden.** `deconcord_output/` now writes CSVs to `tables/` and PNGs to `figures/`, plus a new `run_metadata.json` (DEConcord version, Python version, core dependency versions, exact command, input summary, parameters: enough to reproduce a run without having to remember what was installed at the time). Flagged explicitly in `CHANGELOG.md`'s breaking-changes section with the old-to-new path mapping, per the brief's own instruction not to change things like this silently.

**Docs that didn't exist before:** `LICENSE` (MIT, the repo had none), `CITATION.cff` (software-only, explicitly says there's no paper, since there isn't one), `CONTRIBUTING.md`, `SECURITY.md`, GitHub issue/PR templates, and `METHODOLOGY.md`. The last one specifically documents what each concordance metric computes, cites the actual literature for the two that are standard statistics (Jaccard: Real & Vargas 1996; Pearson/Spearman: their 1895/1904 originals), and is explicit that "directional agreement" is *not* a named statistic. It's a deliberately plain literal fraction, not dressed up as something more established than it is.

**Tests.** Split `test_differential_expression.py` (554 lines, three unrelated sections, welch, moderated, covariates, growing in the same file) into three files along those natural boundaries. No test content changed. Audited coverage against the brief's explicit edge-case list (zero counts, missing metadata, mismatched samples, constant expression, tiny samples, NaN/infinite values, duplicate gene IDs, invalid thresholds) and found two real gaps: `validate_counts` had no direct test that duplicate gene IDs actually raise (only the underlying `check_unique_index` helper existed, untested itself), and no test at all covered infinite values. Added both.

**One example, not several.** `examples/quickstart.py` generates a small deterministic synthetic dataset (fixed seed, 3000 genes with 60 planted true positives, small enough to run in under a second, large enough that a few strongly-shifted genes don't distort CPM normalization for everything else, which is what happened in an earlier, smaller draft of this dataset), then runs the actual intended workflow: load, validate, two DE methods, concordance between them, a volcano plot. No network, no R. One polished script over several partial notebooks, per the brief.

**What deliberately didn't happen.** No `study.compare_methods()`-style object-oriented API. The brief itself said not to force this if it'd require unsafe refactoring, and curating the existing functional API's exports was the safer version of the same goal. No threshold sensitivity, pathway stability, or resampling stability. `METHODOLOGY.md` documents them as specifications, not implementations, exactly as the brief asked. No PyPI publish, explicitly out of scope unless asked for directly.

Decisions rejected along the way:

- **The brief's literal flat-file module layout** (`io.py`, `qc.py`, `differential_expression.py`, single files at the top of `src/deconcord/`). Rejected in favor of keeping the existing subpackage structure and only moving it under `src/`. See Structure above.
- **Auto-fixing every `ruff` import-sort finding** (`I001`), which showed up across nearly every file once linting was turned on at all. ## Aug 15: threshold sensitivity and pathway stability (v0.14.0)

The roadmap has said "next: threshold sensitivity, pathway stability" since the DEConcord rename on Aug 14. Both are built now, and both work exactly the way the Aug 14 rename entry said they would: as thin layers on top of the concordance machinery that already existed, not new statistical ideas.

**Threshold sensitivity.** Added `compute_threshold_sensitivity` to a new file, `concordance/threshold_sensitivity.py`. It calls `compute_de_concordance` once per alpha in a supplied list (default `(0.01, 0.05, 0.1)`) and collects two things: an alpha-indexed summary table (how Jaccard index, significant counts, and directional agreement move as the threshold moves), and a per-gene table of what fraction of the swept alphas call that gene significant in each table.

The one real design decision was what "stable" means. A gene could be stable in the sense that both tables agree about it at every threshold, or stable in the narrower sense that each table's own call about it doesn't flip within the swept range, regardless of whether the two tables agree with each other. Went with the second, narrower definition: `stable_genes` requires both tables' own significance fraction to be 0.0 or 1.0, independently. A gene significant at every alpha in table A and non-significant at every alpha in table B counts as stable, even though A and B disagree about it, because that disagreement isn't a threshold artifact, it's a real, consistent difference between the two tables. Conflating "the tables disagree" with "the call is threshold-sensitive" would have hidden exactly the genes worth looking at closely: consistent disagreements, not borderline ones.

Deliberately left `pearson_r_lfc`/`spearman_r_lfc` out of the by-alpha summary table. Both are computed across every compared gene, not just the significant ones, so they don't depend on alpha at all, they'd just print the same number on every row of a table meant to show what changes with alpha.

**Pathway stability.** Added `compute_pathway_stability` to `concordance/pathway_stability.py`. Same overlap-and-Jaccard core as `compute_de_concordance`'s significant-gene comparison, but applied to two pathway enrichment tables instead of two gene-level DE tables.

The scope decision here was leaving out a directional-agreement or correlation component, even though `compute_de_concordance` has both. Pathway enrichment tables don't have a shared, comparable effect-size column the way DE tables share log fold change: local enrichment (`run_pathway_enrichment_analysis`) reports an `overlap_count` against whatever background the caller supplied, live g:Profiler (`run_gprofiler_enrichment`) reports an `intersection_size` against its own background, and the two numbers aren't measuring the same thing even when they're comparing the same pathway. Correlating them would have produced a number with no defensible interpretation. Comparing presence/absence of significance is the part that's actually well-defined regardless of which enrichment source produced either table, so that's the entire feature: significant-pathway overlap, Jaccard index, and explicit stable/method-specific pathway name lists. Column names are configurable (`pathway_col_a`/`pvalue_col_a`/etc.) for the same reason `compute_de_concordance`'s are: local enrichment uses `pathway`/`adjusted_p_value`, live g:Profiler uses `name`/`p_value`, and neither should have to be renamed just to be compared.

**Public API and docs.** Both functions are exported from `deconcord/__init__.py` (`dc.compute_threshold_sensitivity`, `dc.compute_pathway_stability`), following the same curation pattern the professionalization pass set up. `METHODOLOGY.md`'s "not implemented yet" placeholder section for these two was replaced with full documentation: what each function computes, how to interpret the output, and what it doesn't tell you. Resampling stability is still a specification only, moved to its own section rather than staying bundled with the two that are now real.

19 new tests (9 for threshold sensitivity, 10 for pathway stability), each covering the summary metrics, the gene/pathway-level output, column-name configurability, and the same edge cases the rest of the concordance module already checks for: empty/invalid/duplicate input, no overlap between the two tables, missing columns, NaN handling.

Test count: 186 to 205.

Decisions rejected along the way:

- **Adding a `lfc_threshold` sweep alongside the `alpha` sweep** in threshold sensitivity, since the README's own limitations section has mentioned both as candidates for "threshold sensitivity" since before either was built. Rejected for this pass: `alpha` sweeping is the more immediately useful and more clearly scoped version (it's the exact axis `compute_de_concordance` already exposes), and doing both at once would mean either a 2D sweep (a much bigger surface to test and document well) or two barely-related parameters bolted onto one function signature. `alpha` first; `lfc_threshold` sensitivity is a real, separate follow-up if it turns out to matter in practice.
- **A single "overall stability score" per gene**, collapsing the two tables' fractions into one number. Rejected for the same reason a combined robustness score was rejected in the Aug 14 pivot entry: it would be a composite invented for presentation, not derived from anything statistically meaningful, and it would hide exactly the case (A stable, B stable, but disagreeing) that `stable_genes`'s current definition is built to surface.
- **Reusing `compute_de_concordance`'s exact summary dict shape for pathway stability**, including keys like `pearson_r_lfc` set to `NaN` for consistency. Rejected as actively misleading: a `NaN` in that position could be misread as "correlation was computed but came out undefined," not "this metric doesn't apply here at all." `compute_pathway_stability`'s summary only contains keys that mean something for pathway-level comparison.
- **Making `compute_pathway_stability` try to reconcile different background universes or gene-set collections automatically** (e.g. warning if the two tables' pathway name sets look suspiciously disjoint). Rejected as guessing: there's no reliable way to tell "these two enrichment runs used incompatible gene-set collections" apart from "these two runs legitimately tested different pathways" just from the tables themselves. Documented as a limitation instead of a heuristic that would sometimes be wrong in both directions.

## Aug 16: resampling stability (v0.15.0)

The last of the three "Next" items from the DEConcord pivot roadmap. Method concordance, threshold sensitivity, and pathway stability all ask whether a conclusion survives a different *analytical* choice. Resampling stability asks whether it survives a different *sample set*: rerun the same DE workflow on perturbed groups of samples, holding the method and thresholds fixed, and see how often each gene's significance call reappears.

Added `compute_resampling_stability` to a new file, `concordance/resampling_stability.py`. It runs `run_differential_expression` once on the full sample set as a baseline, then reruns it on a series of perturbed sample sets, and reports a per-gene fraction of reruns that still call each gene significant.

**Two resampling schemes, not three.** `METHODOLOGY.md`'s placeholder for this function (written back on Aug 14) said "bootstrap, subsampling, or leave-one-out." Built subsampling (random subset of each group, without replacement) and leave-one-out (drop each sample exactly once, deterministic and exhaustive). Left bootstrap out: it draws samples *with* replacement, which routinely produces a repeated sample name within a group, and `run_differential_expression`'s own guardrails refuse exactly that, on purpose, to catch a real class of caller bugs (accidentally listing the same sample twice). Making bootstrap work would mean reworking how the DE functions index into the expression matrix, by name today, to tolerate duplicates. That's a bigger change than this function's scope justifies, and subsampling gives the same "how much does the exact sample set matter" signal without it. Documented as a scope decision in the module docstring, `METHODOLOGY.md`, and the README, the same way pathway stability's missing correlation component was documented rather than left as a silent gap.

**What "stable" means here.** Threshold sensitivity's stability check is exact: a gene's call either flips somewhere in the swept alpha range or it doesn't. Resampling is noisier, since each subsample draw is a different random perturbation, so stability needed a tunable margin instead of an exact flip check. A baseline-significant gene counts as stable if it's significant in at least `stability_threshold` (default 0.9) of reruns; a baseline-non-significant gene counts as stable if it's significant in at most `1 - stability_threshold` of reruns. Restricted `stability_threshold` to `(0.5, 1.0]`, since below 0.5 "stable" would stop meaning "reappears most of the time."

**Testing this took more care than the other two.** Threshold sensitivity and pathway stability both take pre-computed result tables as input, so their tests could hand-construct exact p-values and know precisely what should happen. Resampling stability runs real Welch's t-tests internally, on real (if tiny) fixture data, so the test fixtures had to be checked against an actual run of `run_differential_expression` before the expected values got hardcoded into the test file, the same way `compute_pvalues`'s own tests check `< 0.05` rather than an exact p-value. Built a small three-gene, three-samples-per-group fixture: one gene with a huge, low-noise gap between groups (stays significant no matter which sample gets dropped), one with near-identical means (never significant), and one genuinely borderline, significant with every sample present, but only 4 of 6 leave-one-out reruns preserve that call, deliberately below the 0.9 threshold, so it comes out sensitive despite being significant in the baseline. That third gene is the actual point of the feature: a finding that looks solid until you check whether it depends on two specific samples.

**Public API and docs.** Exported from `deconcord/__init__.py` (`dc.compute_resampling_stability`). `METHODOLOGY.md`'s resampling stability section was rewritten from a specification into full documentation, matching the pattern set for the other two. Also caught and fixed a leftover bug in this file from the Aug 15 entry above: it said "Version bump: 0.13.1 to 0.13.2" when it should have said "0.13.2 to 0.14.0." Fixed in place rather than left as a footnote, since a devlog that misreports its own version history isn't trustworthy about anything else in it.

14 new tests, covering both resampling modes, the summary and per-gene output, reproducibility under a fixed `random_state`, and the validation errors (bad `resample_method`, bad `stability_threshold`, `n_iterations`/`subsample_fraction` out of range, a subsample fraction that would leave fewer than 2 samples in a group, too few samples for leave-one-out).

Test count: 205 to 219.

Decisions rejected along the way:

- **Bootstrap resampling.** Covered above. Rejected for this pass, not forever: if it turns out to matter, the right fix is reworking the DE functions' sample indexing, not bolting a workaround onto this module.
- **A single combined resampling-stability score per gene**, collapsing `frac_significant` into a pass/fail on its own. Rejected for the same reason every other combined score in this project has been rejected so far: `is_stable` already exists as the pass/fail version, computed from `frac_significant` and `stability_threshold`, and hiding the underlying fraction behind it would throw away exactly the information (how close to the threshold a gene actually is) that makes a "sensitive" verdict useful rather than just a label.
- **Defaulting `resample_method` to `"leave_one_out"`** instead of `"subsample"`. Leave-one-out is deterministic and needs no `random_state`, which sounds like the safer default. Rejected because it's also a much gentler perturbation (only ever drops one sample, and only from one group at a time), and a small dataset's leave-one-out run can look artificially stable just because dropping a single sample rarely moves a group mean much. Subsampling, drawing a smaller group each time, is a more informative default stress test, at the cost of needing enough iterations and a random seed for reproducibility.

Version bump: 0.14.0 to 0.15.0.

## Aug 17: a CLI subcommand for concordance (v0.16.0)

The roadmap's "Later" bucket has had "a CLI subcommand for the concordance functions, once there's more than one interface question to answer than 'run the pipeline on one count matrix'" sitting in it since the resampling stability entry above. There are now three concordance functions and a stable core one (`compute_de_concordance`), so the interface question has an actual answer. Built `deconcord concordance results_a.csv results_b.csv`, a thin CLI wrapper around `compute_de_concordance`.

**The one real design decision: don't touch the existing CLI shape.** The original invocation, `deconcord counts.csv --group1 ... --group2 ...`, has no subcommand name at all, it's a bare positional argument. Making `concordance` a real argparse subparser the conventional way would mean introducing a `run` subcommand too and breaking every existing invocation of that bare form, including the one in this project's own README, CI, and roughly twenty existing CLI tests. Pre-1.0 SemVer would allow that kind of breaking change in a minor bump, the CHANGELOG says so explicitly, but "allowed" isn't the same as "worth doing for its own sake." Instead, `main()` checks whether the first argument is literally the string `"concordance"` and dispatches to the new code path if so; anything else falls through to the original, completely untouched `_run()`. Cheaper, and every existing test and script keeps working exactly as it did.

The one honest cost of that choice, documented in the module docstring: a count matrix file literally named `concordance` would get misread as the subcommand instead of a file path. Rare enough not to be worth a heavier parser for.

**What the subcommand writes.** Same reproducibility convention as the pipeline CLI: a `run_metadata.json` with version, timestamp, and every parameter used. Plus `summary.json` (the flat metrics dict), `merged.csv` (every compared gene, both tables' values side by side, gene ID as an explicit column instead of a bare index), and one CSV each for `concordant_genes`, `discordant_genes`, and `only_in_<name>` for both tables. Column names (`--lfc-col-a`, `--pvalue-col-a`, etc.) and the gene ID column (`--gene-id-col-a`, default: first column in the file) are all configurable, mirroring `compute_de_concordance`'s own parameters, since a DESeq2 CSV and an edgeR CSV don't share column names and neither should have to be renamed just to be compared from the terminal.

Added two small CSV fixtures (`tests/fixtures/concordance_a.csv`, `concordance_b.csv`, four genes with known, by-hand-computed concordance numbers) plus a DESeq2-style-column variant, so the CLI tests check real, specific numbers (jaccard = 2/3, two concordant genes, zero discordant) rather than just "it ran without crashing." 14 new tests, including one explicit regression test confirming the bare pipeline invocation is untouched.

Test count: 219 to 233.

Decisions rejected along the way:

- **A proper `run`/`concordance` subparser split.** The conventional argparse way to do this. Rejected because it breaks the existing bare invocation for no functional gain, "conventional" isn't a strong enough reason to break every script anyone's already written against this CLI.
- **CLI subcommands for threshold sensitivity and pathway stability at the same time.** Both take two input tables and a handful of parameters like `compute_de_concordance` does, so it'd be easy to add both now. Rejected for this pass: better to see whether the `concordance` subcommand's actual shape (flag names, output file layout) holds up once it's been used, instead of locking in three CLI surfaces on the same untested guess about what shape is right.

## Aug 19: a third tool for method concordance (v0.17.0)

The README's roadmap has said "a third DE tool, harder data regimes" was next since the limma-voom benchmark work started. DESeq2 and edgeR agreeing strongly with each other is a real finding, but it's a finding about two tools, and two tools that happen to be the two most commonly paired in RNA-seq tutorials. limma-voom is the obvious third: independently developed, widely used, a different statistical approach (linear modeling on voom-transformed observations with precision weights, instead of a negative-binomial GLM) from either of the other two.

**`benchmarks/run_limma_voom.R`.** Standard limma-voom workflow -- `DGEList` -> `filterByExpr` -> `calcNormFactors` (TMM) -> `voom` -> `lmFit` -> `eBayes` -> `topTable` -- on the same `airway` and `pasilla` datasets and the same group comparisons `run_deseq2_edger.R`/`run_deseq2_edger_pasilla.R` already use. Not tuned toward agreeing with anything. Data loading is duplicated from those two scripts rather than shared, on purpose, so this script stays runnable on its own; it doesn't rewrite `benchmarks/data/` since the raw counts would be byte-identical to what those scripts already write there.

**`benchmarks/method_concordance.py`** now loops over all three pairs (DESeq2 vs edgeR, DESeq2 vs limma-voom, edgeR vs limma-voom) on both datasets instead of running DESeq2 vs edgeR alone. The DESeq2-vs-edgeR numbers are byte-identical to before the change -- checked, not assumed. Also added two derived metrics the benchmark script computes on top of `compute_de_concordance`'s own output: the significant-gene union (not just the intersection `compute_de_concordance` already reports), and a directional-agreement check widened to genes significant in *either* tool, not just genes significant in *both* (`compute_de_concordance`'s own `directional_agreement` is scoped to the "both" case, which says nothing about the far more common case of a gene one tool calls significant and the other doesn't). These stayed in the benchmark script, not the library -- see "Decisions rejected" below.

**The 30-gene airway puzzle.** The three pairwise comparisons don't share the same "genes compared" count: 15,896 for both pairs involving DESeq2, 15,926 for edgeR-vs-limma. The easy, wrong assumption would have been "DESeq2's independent filtering," since that's the standard reason a DESeq2 gene set differs from another tool's. Checked instead of assumed: pulled the 30 genes and looked at their raw `pvalue`/`padj` values in the DESeq2 output. Independent filtering nulls only `padj`, keeping `pvalue`; these 30 genes have *both* null. That's DESeq2's separate Cook's-distance outlier flag, not independent filtering. Corroborated against the raw count matrix: these 30 genes have a much higher single-sample share of their total count (median 0.42, several above 0.6) than the baseline of the other 15,896 kept genes (median 0.18), consistent with the single-sample-leverage signature Cook's distance is built to catch. `compute_de_concordance`'s existing `dropna` step (drops any gene missing lfc/padj in either table) fully and correctly accounts for the gap -- no join or identifier bug.

**Quantifying discordance instead of eyeballing it.** Earlier spot-checking suggested disagreement clusters near the 0.05 threshold. Replaced that with a full pass: every gene significant in exactly one method, for all six dataset x pair combinations, binned by how far the non-significant side's adjusted p-value sits past 0.05. Holds up: 83-100% of discordant genes per comparison have a non-significant-side padj within 0.10, and direction agreement among discordant genes is 100% in every one of the six comparisons -- not just the pairs or the subset that got spot-checked before. But it isn't purely a thresholding story for the limma-voom pairs: both airway limma comparisons have a real tail, one gene in particular (`ENSG00000171819`, raw counts `4, 50, 19, 543, 1, 10, 14, 1067` -- a low-count gene with two very large single-sample values) where DESeq2 (padj 0.0006) and edgeR (FDR 0.039) both call it significant and limma-voom doesn't (adj.P.Val 0.427), with the log fold change itself diverging (5.80 / 5.78 vs. 4.05), not just the p-value. Direction still agrees. Left as an open, named case rather than folded into the "it's all just threshold noise" narrative, since it isn't.

**Docs.** README's validation table extended from 2 rows (one per dataset) to 6 (one per dataset x pair). `docs/index.html`'s concordance section reused its existing three-tile `.stat-row` layout (no new CSS -- the grid already wraps at multiples of 3) to show Jaccard per pair instead of per dataset, and its note paragraph now mentions all three tools and links to the diverging-gene tail instead of implying every disagreement is threshold noise.

Decisions rejected along the way:

- **Assuming the 30-gene gap was independent filtering** because that's the familiar DESeq2 explanation. Rejected as a shortcut -- checked both `pvalue` and `padj`, and checked the raw counts, before writing anything down as the explanation.
- **Softening the `ENSG00000171819` tail into "more of the same threshold noise."** It would have made a tidier interpretation paragraph. Rejected because the log fold change itself diverges there, not just the adjusted p-value -- collapsing that distinction back into "it's all thresholding" would misreport the diagnostic that specifically went and checked for it.
- **Moving `significant_union`/`directional_agreement_any_significant` into `compute_de_concordance` itself.** They're useful, but they're benchmark-specific questions ("what about the genes only one tool flags") layered on top of the library's existing contract, not something every caller comparing two DE tables necessarily wants back by default. Kept in `benchmarks/method_concordance.py` for this round; revisit if they turn out to matter enough to belong in the library.
- **A CI job running the R benchmark scripts.** Would need Bioconductor in CI (`DESeq2`, `edgeR`, `limma`, plus the `airway`/`pasilla` data packages), a heavier and slower dependency than this project's CI has needed so far. The benchmark results stay a manually-run, manually-committed record instead, same as before this round.

No tests added: `benchmarks/` has never had pytest coverage (the R scripts and `method_concordance.py` are validated by inspection and by the diagnostic pass documented above, not by a test suite), and this round doesn't change that boundary. ## Aug 19: direction and rank stability, from reruns already sitting there (v0.18.0)

`compute_resampling_stability` already reruns DE on perturbed sample sets and already computes a `log_fold_change` per gene per rerun -- it's just been throwing that number away the moment it checked `significant`. Two more robustness questions turn out to be answerable from that same, already-paid-for number: does a gene keep pointing the same direction under perturbation (`direction_stability`), and does it keep roughly the same position relative to every other gene (`rank_stability`). Neither needed a new DE call, a new resampling mode, or a new significance criterion -- the brief was explicit about all three, and the existing loop already had everything required.

**`direction_stability`.** Pure sign comparison: for each gene, what fraction of reruns have the same `sign(log_fold_change)` as the baseline, restricted to reruns where that gene's log fold change is actually a finite number. No p-value anywhere in the formula, on purpose -- `frac_significant`/`is_stable` already answer "does this gene keep clearing the significance bar," and folding a significance check into this metric too would make it redundant instead of complementary. A gene can be significance-fragile (barely clears 0.9 `stability_threshold`) while still being direction-stable at 1.0: the sign was never actually in question, only the exact p-value's relationship to a threshold.

**`rank_stability`.** The harder one to get right, and the one place the brief was most specific: a per-gene score, not one Spearman correlation shared by every gene. Ranked genes by signed log fold change within each run (baseline and every rerun independently), normalized to a percentile in `[0, 1]`, then scored each gene as one minus its mean absolute percentile deviation from baseline across reruns. Signed, not `|lfc|` and not p-value, so it measures relative effect-size position -- a different axis from both `direction_stability` (this gene's own sign) and `frac_significant` (this gene's own call rate). The subtlety that took the most care: a gene's own log fold change can stay exactly the same across every rerun and its rank can still move, if some *other* gene's value swings past it. That's not a bug, it's what "relative position" means -- built a six-gene fixture specifically to demonstrate it (`top`'s own log fold change never changes, but its `rank_stability` still drops to 14/15 because `swap` occasionally overtakes it).

**Denominator, made explicit rather than assumed.** Both metrics restrict their average to reruns where *that specific gene's* rerun log fold change is a finite number -- not `n_iterations` blindly. In practice this is almost always the same thing: `log_fold_change` is a plain difference of means on real data, so a real DE rerun essentially never produces a non-finite value for it. But "essentially never" isn't "provably never," and the brief asked for explicit handling, so both metrics compute a per-gene denominator and document it rather than silently assuming every rerun contributed. Also handled: a gene with baseline log fold change of exactly 0 has no direction to be stable or unstable relative to (`direction_stability = NaN`), and fewer than 2 rankable genes makes `rank_stability` undefined (`NaN`).

**Testing the denominator/NaN behavior meant testing below the public function.** A real `run_differential_expression` rerun won't produce a NaN log fold change from valid input -- there was no honest way to make `compute_resampling_stability` itself exercise the "invalid rerun" branch without fabricating a broken input matrix, which would test something else entirely (the DE function's own NaN handling, not this module's). Extracted the per-gene computation into two private, directly-testable functions (`_direction_stability`, `_rank_stability`) instead, and unit-tested those directly with hand-built `pd.Series`/`pd.DataFrame` containing explicit `NaN` entries -- deterministic, and it tests the actual documented rule instead of hoping a contrived integration scenario exercises it. Everything else (does it wire into `compute_resampling_stability` correctly, do the summary means use baseline-significant genes only, does `is_stable` stay untouched) is tested through the public function, same as every other test in this file.

**Fixture design took longer than the implementation.** Wanted every expected number hand-derivable and exact, same standard the Aug 15 resampling-stability fixture set (`benchmarks/`-adjacent). Two new fixtures: `_direction_df` (uniform-within-group genes for "always stable," one gene designed so dropping one specific sample flips its sign) and `_rank_df` (six genes, two -- `anchor`/`ceiling` -- placed far outside the one moving gene's range so they're provably always rank 1 and rank 6, and one, `swap`, deliberately non-uniform so its value swings past three other genes across the six leave-one-out drops). Every asserted fraction (`5/6`, `13/15`, `29/30`, `17/18`, ...) was computed by hand against the six leave-one-out iterations before being hardcoded, then checked against the actual implementation, not the other way around.

**Public API.** No new top-level function -- `direction_stability`/`rank_stability` are new columns on the existing `gene_stability` DataFrame, `mean_direction_stability`/`mean_rank_stability` are new `summary` keys, both computed inside `compute_resampling_stability`. `_direction_stability`/`_rank_stability` stay module-private; nothing about them is part of the public contract, they're just where the per-gene math lives so it's testable in isolation.

`research/ml/` untouched, as scoped -- these are core `deconcord.concordance` metrics, available if a later ML pass wants them, not built for that pass.

Decisions rejected along the way:

- **Ranking on `|log_fold_change|` instead of the signed value**, which would measure "how extreme is this gene's effect" without conflating it with direction. Rejected because it would make `rank_stability` partially redundant with `direction_stability` doing the same sign-blindness job twice from two different angles; ranking signed keeps the two metrics answering genuinely different questions (own sign vs. relative position among signed effects), which is what "don't collapse into the same information" asked for.
- **A single combined "effect stability" score merging `direction_stability` and `rank_stability`.** Same reasoning every combined score in this project has been rejected for before: the two component numbers carry different, useful information on their own (a gene can be direction-stable and rank-unstable, or the reverse), and collapsing them would throw that apart away.
- **Normalizing `rank_stability`'s percentile denominator against the baseline's valid-gene count in every rerun, instead of each rerun's own valid-gene count.** Would make the two percentiles more directly comparable in the pathological case where a rerun's valid gene set actually differs from the baseline's. Rejected as needless precision for a case that essentially can't happen with real DE output (baseline and every rerun run on the same gene index), and documented the actual per-rerun-count behavior instead of quietly picking whichever seemed safer.

12 new tests (14 to 26 in `test_resampling_stability.py`), covering: `direction_stability` at 1.0 when consistent, decreasing on a hand-verified sign flip, NaN on a zero baseline, denominator behavior via the private function directly; `rank_stability` at exactly 1.0 for genes provably outside another gene's range of movement, decreasing (with exact hand-derived fractions) when a gene's rank genuinely moves, denominator behavior via the private function, NaN on a missing baseline; both metrics' bounds; summary means restricted to baseline-significant genes (checked against the actual `baseline_significant` column, not assumed); and one explicit regression test pinning `gene_stability`'s column list and `is_stable`/`stable_genes`/`sensitive_genes` to their pre-existing values on the original fixture. Full pytest suite: 235 to 247. `ruff check src/ tests/ benchmarks/ examples/`: clean.

Version bump: 0.17.0 to 0.18.0.

## Aug 20: closing out the airway/pasilla discovery phase for the rank-stability hypothesis

No package version bump in this entry, on purpose. Everything below happened in `research/ml/`, consuming the `direction_stability`/`rank_stability` metrics v0.18.0 shipped, not changing `src/deconcord/` at all. Worth saying plainly rather than letting a devlog entry with no version line at the bottom look like an oversight.

The question this research track was scoped to test back when it started: do DEConcord's own robustness metrics carry predictive information about cross-method agreement beyond what conventional DE statistics already give you. Across the whole gene set, they mostly don't, conventional features alone hit PR-AUC around 0.97 predicting whether edgeR agrees with a DESeq2 call, and robustness features move that only slightly. That's not a null result to hide, it's exactly what you'd expect: most genes aren't ambiguous, and an ambiguity-detecting feature has nothing to detect on them.

The regime where it mattered: genes DESeq2 itself is unsure about, adjusted p-value between 0.01 and 0.10. Several rounds of checking there, in roughly the order they happened: an unlocked logistic regression comparison (conventional PR-AUC 0.67/0.50 depending on train/test direction, +`rank_stability` pushing to 0.74/0.64), a residualization check (fit `rank_stability` against `abs_logfc`/`neg_log10_p` and use only what's left over, the gain survived, so it isn't just effect size and p-value under a different name), a five-window sensitivity sweep (the gain held in 9 of 10 window x direction combinations, not one lucky threshold), and bootstrap uncertainty intervals over the test genes (7 of 10 settings clearly positive, 2 crossing zero, 1 clearly negative in the sparsest window tested, `pasilla -> airway` at 0.05-0.10, reported as-is rather than dropped for being inconvenient).

Then the part I'd actually point to if pressed for one number: a locked evaluation. L1-penalized logistic regression, regularization strength chosen by 5-fold cross-validation on the training dataset alone, then locked and scored exactly once on the untouched held-out dataset, the closest this track has come to a real train/select/test split instead of comparing PR-AUC at whatever hyperparameter happened to be sitting there. `pasilla -> airway`: conventional PR-AUC 0.5017, ROC-AUC 0.8520; adding `rank_stability`, PR-AUC 0.6504, ROC-AUC 0.8843, delta +0.1487, `rank_stability`'s own coefficient +2.4305, the largest-magnitude coefficient in the model. Two more checks backed it up: an L1 sweep confirming `rank_stability` keeps a nonzero coefficient across every regularization strength tried, not just the one CV happened to pick, and a matched-C comparison (same `C` for both feature sets, instead of separately tuning one per set) confirming the combined model stays ahead at every strength on the grid, not just at the specific values each model's own tuning landed on.

`direction_stability` never contributed anything in this regime, it's exactly 1.0 for every gene in the borderline subsets tested (a gene near DESeq2's own significance boundary apparently still keeps a consistent effect sign across leave-one-out reruns, even while its significance call itself wobbles), so it has zero variance to split on. `significance_stability` was dropped even earlier, DEConcord's own baseline significance calls are too sparse for a fraction-of-reruns-significant feature to discriminate on, especially on `airway`. The entire finding is `rank_stability`, specifically, not a general "add robustness features" result.

What this is and isn't. It predicts whether a second DE method agrees with a first method's borderline call, cross-method agreement, not biological replication, which stays the project's actual long-term target and needs paired discovery/replication datasets this project doesn't have yet. It's been checked on exactly two datasets. The borderline window itself was chosen after an initial look at the all-gene result was uninteresting, post-hoc, not pre-registered, even though the five-window sweep afterward showed it wasn't a fluke of that specific choice. Genes within a dataset aren't independent (co-regulation), so both the cross-validation and the bootstrap intervals have a smaller effective sample size than their gene counts suggest, and neither substitutes for a genuinely independent third dataset. All of this is written down in full in `research/ml/FINDINGS.md`, which is now the primary record of this result, `INVENTORY.md` and `EXPERIMENTAL_REPORT.md` were also corrected in the same pass, both had gone stale describing a version of the feature tables from before the robustness columns existed.

Decisions rejected along the way:

- **Reporting only the strongest (locked) number and quietly dropping the earlier, weaker comparisons.** Rejected. The unlocked borderline result, the residualization check, the window sweep, and the bootstrap intervals are what built confidence in the locked result being real rather than a fluke of one particular modeling choice; cutting them would make the finding look more sudden and less earned than it actually was.
- **Hiding the one negative bootstrap window.** It's the sparsest window tested and the least trustworthy number in the whole set, but a finding that gets to hide its own worst case isn't an honest finding. Kept, with the sparsity noted as the likely reason, not as an excuse to discount it.
- **Bumping the package version for this.** Nothing in `src/deconcord/` changed. A version bump implies a package change; using one to mark a research milestone would misuse the same signal the changelog discipline exists to keep meaningful.
- **Moving straight to a more complex model now that the logistic-regression result looks real.** Rejected for the same reason a bootstrap CI over two datasets' worth of genes isn't evidence of cross-dataset generalization: a fancier model fit to the same two datasets risks fitting dataset-specific quirks harder, not finding something more true. Next real step is a third, independent dataset under this same frozen experiment design, not a bigger model on the same two.

No version bump: this entry documents `research/ml/` work only. Current package version stays 0.18.0.

Fourth external dataset for the frozen ML endpoint (see the previous entry and `research/ml/FINDINGS.md`'s zebrafish section for why a fourth, higher-powered dataset was needed: zebrafish's 3-vs-3 design turned out to have zero edgeR-significant genes at all, non-evaluable for the borderline-window target, not a negative result). Replacement route: `recount3`, pulling the same underlying study straight from SRA instead of through a downstream Bioconductor object. Verified before writing any code, not assumed: `organism = "mouse"`, `data_source = "sra"`, project `SRP004777` genuinely exists in recount3's hosted files (fetched its metadata file directly, got real content back, not a 404), and NCBI's own SRA listing for SRP004777 shows 21 runs with titles following a `{strain}_{replicate}_{lane}` pattern (`B6_1_7`, `D2_2_4`, etc.) consistent with the verified 10 B6/11 D2 design.

Same defensive shape as the dexus script's own validation, just applied across an unknown column set instead of one assumed one.

Output contract unchanged on purpose: `benchmarks/data/bottomly_counts.csv`, `benchmarks/data/bottomly_metadata.csv`, `benchmarks/results/bottomly_deseq2_results.csv`, `benchmarks/results/bottomly_edger_results.csv`, same columns as before. `compare_results.py`, `build_tables.py`, and `generate_robustness.py`'s `run_bottomly` (which already reads B6/D2 membership from `bottomly_metadata.csv` at runtime rather than a hardcoded list) needed no changes.

This sandbox has no R and can't run the script; it's written, defensively validated, and ready for a real R environment to execute. Ran what the sandbox can check: `pytest -q` and `ruff check src/ tests/ benchmarks/ examples/` against the unchanged Python layer, both clean, confirming this R-only rewrite didn't touch anything Python depends on.

Decisions rejected along the way:

- **Guessing the recount3 colData() column name for strain** (e.g. assuming it's called `sra.sample_title`) instead of scanning all columns at runtime. ## Aug 20: starting the stress-test suite, regime 1: unbalanced groups

The README's roadmap has named this "Next" for a while: a stress-test benchmark suite, a third DE tool plus harder data regimes, to check how method concordance behaves outside the two clean, balanced two-group datasets checked so far. Two things worth naming before describing what actually got built today.

First, the "third DE tool" part turned out to already be done. `benchmarks/run_limma_voom.R` and the limma-voom columns in `benchmarks/method_concordance.py` were already committed (`089afce`, Aug 19), with real numbers already in `README.md`'s validation table. That work predates this session; today's pass didn't touch it, just discovered it was already there while scoping this task, worth recording so it's not implied to be new.

Second, given a choice of which harder regime to start with, went with unbalanced groups first (of the three the roadmap names: unbalanced groups, batch effects, low counts), and with synthetic perturbations of a dataset already in hand rather than sourcing a new one, specifically to avoid repeating the acquisition-verification cycle zebrafish and Bottomly both required. "Synthetic perturbation" here means real subsets of real samples, never fabricated expression values -- the thing that changes across a level is which and how many real samples go into each group, nothing about the counts themselves.

Bottomly (21 real samples, 10 B6/11 D2, the most replication of any dataset in hand) is the base. Three levels, `run_stress_unbalanced.R`: `balanced` (10 vs 11, the real full design), `moderate` (5 vs 11), `severe` (2 vs 11). D2 held fixed at its full 11 across every level and only B6 shrunk, deliberately, so the imbalance ratio is the one thing that changes level to level rather than being confounded with "less total data" from shrinking both sides together. 2 is the floor, not 1: DESeq2's dispersion estimate, edgeR's, and limma-voom's `lmFit` all need at least 2 replicates in a group to estimate any within-group variance at all, so n=1 wouldn't be a harder version of this same question, it'd be a different one (can these tools run at all). Which B6 samples make up the `moderate`/`severe` levels is computed at runtime from the metadata actually loaded, sorted sample ID, first N -- not a remembered or guessed list, the same discipline adopted after the zebrafish sample-name mistake. DESeq2, edgeR, and limma-voom each run their own unmodified, default workflow at every level, same as `run_deseq2_edger_bottomly.R` and `run_limma_voom.R` already do, no tuning toward any particular outcome.

Decisions rejected along the way:

- **Shrinking both groups together instead of holding D2 fixed.** Would confound two different stresses (imbalance ratio vs. total sample size) into one number, making the result harder to attribute to either cause specifically.
- **Going to n=1 for the most extreme level.** Rejected, see above -- that's a different question (can the tools run at all) than the one this regime is built to ask.
- **A new, unrelated dataset for this regime instead of Bottomly.** Rejected per the earlier discussion this session: real acquisition work (zebrafish, Bottomly itself) has repeatedly taken multiple rounds to get right, and this regime doesn't need a new dataset to be a real, honest test, it needs real samples split into real, unbalanced groups.

## Aug 20: stress-test regimes 2 and 3, harnesses (not yet run)

Finishing the roadmap's stress-test suite: batch effects and low counts, the last two of the three named "harder data regimes." Both built this pass, neither run against real data yet -- same handoff shape as regime 1's first commit.

**Regime 2, batch effects (`run_stress_batch.R` / `analyze_stress_batch.py`).** The one design decision that took real thought: a batch effect needs a genuine confound to be a genuine test, and inventing one by scaling counts for an arbitrary sample subset would fabricate the exact signal the regime is supposed to be checking for, a real departure from the "no fabricated expression values" rule regime 1 established. Considered and rejected: extracting a real technical field (sequencing lane) from Bottomly's original SRA sample titles via the recount3 metadata column already used for B6/D2 classification. Rejected only because that column's exact name isn't known without another live R round-trip to check it, and guessing it wrong risked silently building the regime on a nonexistent or misread field. Landed on something both real and immediately available: per-sample library size, computed directly from the real count matrix, no acquisition step needed. Samples split into `low_depth`/`high_depth` by a median split on that real value -- a genuine technical property, and exactly the kind of thing that produces real batch effects in practice (different runs, lanes, or prep batches routinely differ in depth). Two design formulas run through all three tools: `naive` (`~condition`) and `adjusted` (`~depth_batch + condition`). Whether the real split happens to correlate with condition gets reported directly, not corrected for or hidden -- a real confound between technical and biological variables would itself be part of what this regime is checking, not noise to clean up first.

**Regime 3, low counts (`run_stress_lowcounts.R` / `analyze_stress_lowcounts.py`).** More straightforward: binomial thinning, each real read kept with a fixed probability and dropped otherwise, the same well-established technique behind rarefaction and tools like `DropletUtils::downsampleMatrix`. Three depths on the same real 21 samples and groups: `full` (real, unmodified), `moderate` (25%), `low` (5%), fixed seed for reproducibility. Only ever removes real reads, never adds anything that wasn't there -- the same "real subset, not fabricated signal" standard regime 1 and regime 2 both hold to, just applied to reads instead of samples.

Both Python analysis scripts (`analyze_stress_batch.py`, `analyze_stress_lowcounts.py`) follow `analyze_stress_unbalanced.py`'s exact shape: load whatever the matching R script produced, hand each tool pair to `deconcord.concordance.methods.compute_de_concordance`, write a markdown summary plus a comparison table (naive-vs-adjusted for batch, a depth gradient for low counts). Validated both end to end against throwaway mock data (structurally matching what the real R scripts will produce), confirmed clean runs with sensible-looking output, then deleted the mock data and its output before committing -- same discipline as regime 1's validation pass, nothing fake left where a real result belongs.

`benchmarks/results/stress_batch/` and `benchmarks/results/stress_lowcounts/` added to `.gitignore`, same policy as `stress_unbalanced/`: per-run metadata and full result tables are regenerated by the scripts, the summary markdown is the committed record once a real run exists.

Decisions rejected along the way:

- **A fabricated/simulated batch effect (synthetic per-gene multiplicative shift on an arbitrary sample subset).** This is standard practice in some DE-benchmarking literature, but rejected here specifically because it would plant the exact signal (a batch-driven expression shift) the regime exists to detect, making a positive result partly circular. A real, data-derived covariate (library size) answers a narrower question honestly instead of a broader question by construction.
- **Guessing the recount3 sample-title metadata column for a "real sequencing lane" batch variable.** Same reasoning as every other "don't guess a column name or sample identity without checking" decision this project has made since the zebrafish mistake -- library size was available without that risk.
- **Downsampling reads with a different method (e.g., uniform truncation instead of binomial thinning).** Binomial thinning is what the standard tools in this space actually do and is proven to approximate genuine lower-depth sequencing statistically; there was no reason to invent a different, unvalidated thinning rule.

No `src/deconcord/` changes, no version bump -- `benchmarks/` infrastructure only. `pytest -q`: 247 passed. `ruff check src/ tests/ benchmarks/ examples/`: clean.

**Two real-data compatibility gaps, each confirmed by actually running a realistic input before touching any code.** `validate_counts` required literal integer dtype, which rejects salmon/kallisto/RSEM's legitimately fractional "estimated counts" (multi-mapping reads split across the transcripts they map to) -- confirmed with a synthetic table of values like `12.4`, `340.7`. And `load_count_matrix` hardcoded comma-separated parsing, so a real featureCounts/htseq-count-style tab-separated export collapsed into one unparsed column instead of loading correctly -- also confirmed directly. Relaxed the dtype check to numeric + finite + non-negative (kept `check_all_integer` around as a stricter standalone check for anyone who wants to require whole numbers), and added `sniff_delimiter` (comma vs. tab, gzip-aware) as `load_count_matrix`'s new default, overridable via an explicit `sep`.

**One gap in `compute_de_concordance`/`compute_pathway_stability` that adds a warning, not new behavior.** Both functions inner-join two tables on gene ID or pathway name. A *total* mismatch already raised a clear error; a *partial* one (an Ensembl ID version suffix present in one table and not the other, say) didn't -- it just silently shrank the compared set and looked like a slightly lower Jaccard index, exactly the kind of thing that's easy to misread as a real finding about two methods instead of a data-formatting problem. Added a `UserWarning` when the matched count is under half of the smaller table's own size. Deliberately not an error: a real, large biological difference in what was tested is possible too, and that case shouldn't be blocked, just flagged for a second look.

Fixing `check_nonnegative_counts` turned into a small bug of its own along the way. Once `validate_counts` could accept a non-numeric column without immediately raising (every error gets collected before raising, not stopped at the first one), `check_nonnegative_counts`'s `(df >= 0)` blew up with a raw `TypeError` on a string column instead of contributing a clean error to the batch. Restricted it to numeric columns via the same `select_dtypes` guard `check_all_finite` already used, so it fails the way every other check in this file does instead of crashing the whole validation pass.

Decisions rejected along the way:

- **A heuristic warning for "this data looks already normalized," alongside the fractional-counts relaxation.** Tempting, since relaxing the integer check also means DEConcord no longer rejects a CPM table fed in by mistake. Rejected for this round -- "looks pre-normalized" is a fuzzier problem than the concrete one that was actually confirmed (salmon/kallisto-style counts specifically), and building it now would mean solving a problem nobody's hit yet instead of the one that was.
- **Auto-stripping featureCounts' leading annotation columns (`Chr`/`Start`/`End`/`Strand`/`Length`) as part of the delimiter fix.** Checked what actually happens once the delimiter is fixed: a raw featureCounts file now parses into real columns instead of garbage, and `validate_counts` correctly names `Chr` as the problem instead of failing somewhere unhelpful downstream. That's the right amount of fixing for this round -- the delimiter was a bug; dropping metadata columns DEConcord was never asked to guess about is a different feature.
- **Making the gene-ID-mismatch check an error instead of a warning.** A large but real biological non-overlap between two DE tables is a legitimate result DEConcord shouldn't block; the point is to make a likely data problem loud, not to assume it's always one.

Full pytest suite: 247 to 272 (25 new tests, plus a couple of existing ones -- `test_validate_counts_invalid_raises`, `test_validate_counts_multiple_errors_raises` -- rewritten where the fractional-counts relaxation changed what they were actually testing, since a value they used to assert was invalid is now legitimate input). `ruff check src/ tests/ benchmarks/ examples/`: clean.

Two of these turned up real bugs, not just missing tests:

**`check_nonnegative_counts` was double-counting a missing value as a negative one.** `nan >= 0` evaluates to `False` in pandas, so a single `NaN` cell tripped both the "missing values" check and the "non-negative" check at once, producing a confusing two-line `CountMatrixError` for what was really one problem. `check_all_finite` already had the same shape of issue and had already been fixed by excluding `NaN` from its own comparison -- `check_nonnegative_counts` just hadn't gotten the same treatment. Fixed the same way (`numeric.fillna(0) >= 0`, since a filled-in 0 always passes non-negativity without masking a real negative value elsewhere).

**`compute_resampling_stability`'s summary emitted a `RuntimeWarning: Mean of empty slice`** when writing the test for "the baseline finds zero significant genes." `mean_jaccard_to_baseline` calls `np.nanmean` on the per-iteration Jaccard list; when every iteration (baseline and every resample alike) has zero significant genes, every entry in that list is `NaN`, and `nanmean` on an all-`NaN` array still returns the correct `NaN` but complains about it on the way. That's a real outcome (a strict `alpha`, or a genuinely null dataset), not a hypothetical, so it's worth not leaking warning noise for. Checked for the all-`NaN` case explicitly instead of suppressing the warning blindly.

**Type-hint audit.** Installed `mypy`, ran it against `src/deconcord` with `--ignore-missing-imports`. 17 errors, in three places:

- `io/counts.py`'s `validate_counts`: `errors = []` with no annotation gets its element type inferred from the first thing appended to it, so every different `CountMatrixError` subclass appended after the first one got flagged as incompatible. Annotated it explicitly as `list[CountMatrixError]`, the shared base class every subclass here already extends.
- `concordance/threshold_sensitivity.py`'s `compute_threshold_sensitivity`: `alphas` was typed `list[float]` but defaults to a tuple (`(0.01, 0.05, 0.1)`, deliberately immutable to sidestep the mutable-default-argument footgun) and the function's first line is `alphas = list(alphas)` -- so the real contract was always "any ordered iterable of floats," the annotation just hadn't kept up. Changed to `Sequence[float]`.
- `ai_explanation/methods.py`: `response.content[0].text` assumed the Claude API always returns a `TextBlock`, but the SDK types `content[0]` as a union of every possible block type (tool use, thinking, etc.), only one of which has `.text`. For a plain text-only prompt like this one, it's always actually a `TextBlock` in practice -- but asserted that explicitly with an `isinstance` check and a `TypeError` naming the actual block type received, instead of leaving a hypothetical future API response shape to fail as an opaque `AttributeError` deep in SDK internals. Matches this project's own stated preference (see `CONTRIBUTING.md`'s Code style section) for raising loud and specific over a plausible-looking wrong answer.

`mypy src/deconcord --ignore-missing-imports`: 17 errors to 0. Added it as a required, CI-gated step alongside `ruff` (`.github/workflows/tests.yml`), and to `.[dev]`.

**Packaging metadata.** `pyproject.toml`'s core dependencies (`pandas`, `numpy`, `scipy`, `statsmodels`, `matplotlib`, `scikit-learn`) had no version floors at all since the very first commit -- meant `pip install deconcord` into an old or frozen environment could silently resolve to a years-old, behaviorally-different release instead of failing at install time where the problem is obvious. Added minimum versions, each picked as the oldest release actually compatible with this package's Python 3.9 floor. Also added a `py.typed` marker (PEP 561, an empty file plus a `package-data` entry) now that the whole package passes `mypy` cleanly -- without it, a downstream caller's own type checker would ignore this package's type hints entirely rather than reading them. Verified both by actually building a wheel (`python -m build --wheel`) and checking its contents rather than trusting the config alone: `py.typed` is in the wheel, and `METADATA` lists the new floors and the `mypy`/`pytest-cov` dev-extra additions.

Decisions rejected along the way:

- **Chasing every last missed coverage line, including the ones in `ai_explanation/methods.py` (0%) and `pipeline.py`'s one line that calls it.** Both require a live `ANTHROPIC_API_KEY` and an actual paid API call to exercise -- deliberately excluded from CI coverage for that reason since the project first added the AI-explanation feature, not a gap introduced or overlooked in this pass.
- **Suppressing the `RuntimeWarning` from `compute_resampling_stability` with a blanket `warnings.catch_warnings()` instead of checking for the all-`NaN` case explicitly.** Would have silenced this one, plus any other numpy warning that happened to fire in the same block for an unrelated reason -- checking the specific condition that causes it keeps the fix scoped to the actual problem.
- **An upper version bound on the core dependencies, alongside the new floors.** A library (as opposed to an application) pinning an upper bound on `pandas`/`numpy`/etc. is a common source of dependency-resolution deadlocks for anyone using DEConcord alongside other packages with their own version needs -- floors catch the "too old to work" case without creating a new "too new to install" one.
- **Running `mypy` across `tests/`, `benchmarks/`, and `examples/` too, not just `src/deconcord/`.** `ruff` already covers all four directories, but mypy's value is highest on the actual public API surface; test files lean on patterns (loose fixtures, `pytest.raises` context managers, mock objects) that generate a lot of low-value mypy noise for comparatively little benefit. Scoped to `src/deconcord/`, matching what ships to a user.
