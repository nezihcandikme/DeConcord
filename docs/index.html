How much do DESeq2, edgeR, and limma-voom actually agree?

DEConcord takes DE result tables (DESeq2, edgeR, limma-voom, or anything with a gene ID, a log fold change, and a p-value) and measures how much of the biological conclusion survives the choice of method.

Overview

Two competently-run tools don't automatically agree.

DESeq2 and edgeR can both run correctly on the same count matrix and still call a different set of genes significant. That gap is real information, not noise to average away. DEConcord measures that gap directly instead of picking one tool and treating its output as the answer. The pipeline below (validation through pathway enrichment) is what's left of DEConcord's original, broader RNA-seq toolkit. It's kept as infrastructure that still generates real DE result tables to compare, not as the project's main focus anymore.

01

Is the data even usable?

Non-negative integers, no duplicate gene IDs, no missing values, correct orientation. Checked before anything else runs.

02

Can these samples be compared?

Different sequencing depths, dead or outlier samples, low-count genes. Normalized and filtered before they can quietly bias a result.

03

What actually changed?

Per-gene testing, correction for running thousands of tests at once, and a result that says what it does and doesn't mean.

Built today

DESeq2, edgeR, and limma-voom, on real data: how close is close?

Real numbers from compute_de_concordance, run against real DESeq2/edgeR/limma-voom output on two independent public datasets (airway, human; pasilla, Drosophila), each tool run independently with its own default settings, checked pairwise across all three tools. Full methodology in benchmarks/.

0.76 / 0.78 Jaccard index, DESeq2 vs edgeR (airway / pasilla)
0.72 / 0.77 Jaccard index, DESeq2 vs limma-voom (airway / pasilla)
0.91 / 0.95 Jaccard index, edgeR vs limma-voom (airway / pasilla)

Three established tools, run independently, agree strongly with each other in every pairwise combination. Log fold change Pearson correlation is high across all three pairs (0.99–0.9995), and zero genes get called significant by both members of any pair while disagreeing on direction. The disagreement that exists is almost entirely about which marginal genes clear each tool's own significance threshold, not about direction or magnitude for genes multiple tools agree are real. This is a real finding on two datasets, not a general law about these three tools. Full pairwise numbers, including a small number of low-count, high-variance genes where limma-voom's call diverges more substantially, are in benchmarks/.

The pipeline

Load, validate, inspect, normalize, compare, visualize, interpret.

The same order an analysis actually follows. Every stage is also a function you can call on its own.

1

Count Matrix

A CSV or DataFrame. Genes as rows, samples as columns.

2

Validation

Types, missing values, duplicate IDs, and a heuristic check for a transposed matrix.

3

Quality Control

Library size, genes detected, and MAD-based outlier flags per sample.

4

Normalization

CPM for sequencing depth, log2 scale.

+ optional low-count filtering
5

Differential Expression

Welch's t-test per gene, Benjamini-Hochberg correction, volcano and PCA plots.

6

Pathway Analysis

Hypergeometric enrichment against a background you define, not "every gene that exists." Reads standard .gmt gene-set files directly.

7

Interpretation

Optional plain-language summary of the results, generated on request.

Capabilities

What's actually implemented.

No placeholders. Every item below is a real, tested function you can call today.

Threshold sensitivity

Sweeps method concordance across a range of significance thresholds. Tells you which genes stay significant regardless of the exact cutoff, and which ones only clear it at one end of a reasonable range.

Pathway stability

The same overlap-and-Jaccard comparison as method concordance, applied to two pathway enrichment tables. Does a pathway stay enriched across DE methods, or is the pathway-level conclusion itself method-sensitive.

Resampling stability

Reruns differential expression on subsampled or leave-one-out sample sets. Tells you whether a gene's significance call is a broadly reproducible signal or an artifact of which samples happened to be collected.

Validation with specifics

Errors name the column and the problem, not just "invalid data."

Sample QC

Library size, genes detected, MAD-based outlier detection.

Low-count filtering

Drop genes that never had a chance of being tested meaningfully.

CPM + log2 normalization

Puts samples with different sequencing depths on a comparable scale.

Exploratory DE

Welch's t-test or an empirical-Bayes moderated t-test, Benjamini-Hochberg correction, configurable thresholds.

Covariate-adjusted DE

A per-gene linear model that tests group_1 vs. group_2 while holding a batch, sex, or other covariate fixed, instead of letting it confound the result.

Volcano & PCA plots

Generated straight from the results. No separate plotting step to forget.

Pathway enrichment

Local hypergeometric test against a background you explicitly define, or an opt-in live query against g:Profiler's curated GO/KEGG/Reactome databases. Plus a dot plot of the results.

Optional AI summary

Narrates results that are already computed. Doesn't verify them.

GMT / MSigDB gene sets

Load standard pathway files directly. No hand-converting to a Python dict.

Command-line interface

Run the whole pipeline from a terminal, or compare two existing DE result tables directly with deconcord concordance. No script required either way.

Gene symbol annotation

Attach readable gene names from a local mapping file. No live API call. Original IDs untouched.

GEO data acquisition

Fetch a GEO series' supplementary files and sample metadata straight from a GSE accession.

Infrastructure benchmark

DEConcord's own DE method, checked against DESeq2 and edgeR.

A different question from the concordance numbers above: not "how much do DESeq2 and edgeR agree with each other," but "how close is DEConcord's own from-scratch DE implementation to either one." Real DESeq2 and real edgeR, both run with their own default settings, on the airway dataset, the same one DESeq2's own vignette uses. Methodology and full write-up in benchmarks/.

0.94 / 0.95 Pearson r, log fold change (vs. DESeq2 / edgeR)
1.0 Precision: every gene DEConcord calls significant, both tools also call significant
0.08 / 0.10 Recall: the real, quantified cost of a per-gene test vs. models that borrow power across genes

Reading the recall number honestly: a per-gene t-test misses most of what DESeq2 and edgeR find, because those tools borrow statistical power across thousands of genes with similar expression levels and DEConcord's default exploratory method doesn't. It also never flagged a gene neither of them agreed with. It's a fast first look, not a final answer. Same conclusion the README has stated all along, now with a number attached to it.

The numbers above are the default method (Welch's t-test, no assumptions borrowed across genes). DEConcord also has an opt-in empirical-Bayes moderated t-test that does borrow across genes. On this same real dataset, it found more than double the significant genes (196 to 431) while keeping the exact same 1.0 precision. Different assumptions, not a strict upgrade. Both numbers are real and both are in benchmarks/.

Checked again on a second, independent dataset (pasilla, Drosophila, a different lab, a different experimental design) to see whether this pattern was specific to airway. It wasn't. With the default method, precision stayed 1.0 and recall landed within a couple of points of the first run (0.085 vs. DESeq2, 0.104 vs. edgeR, against 0.075/0.098 on airway). The moderated method held the same relationship too: precision still 1.0, recall roughly doubled over the default (0.174 vs. DESeq2, 0.215 vs. edgeR, close to airway's 0.165/0.217). Two independent datasets now agree on both numbers. Full numbers in benchmarks/.

Experimental, not in the package. Phase closed.

Does DEConcord's own robustness signal predict anything?

A separate, exploratory research track under research/ml/, not merged into deconcord, not installed by pip install, not marketed as an "AI feature." The question: does DEConcord's resampling-derived rank_stability carry predictive information beyond ordinary DE statistics, specifically for genes near a significance decision boundary. Tested on four datasets under one unmodified frozen design. Full writeup, every dataset's numbers, and every caveat, in research/ml/FINDINGS.md.

0.50 → 0.65 airway/pasilla PR-AUC, conventional vs. + rank_stability (gain)
0.95 → 0.92 Bottomly PR-AUC, same comparison (loss)
4 datasets 2 evaluable each direction, 1 non-evaluable (zebrafish). Phase closed.

DeConcord's resampling-derived rank stability showed incremental predictive value for borderline cross-method significance agreement in airway/pasilla transfer experiments, but the benefit did not generalize universally: it decreased performance on Bottomly, while zebrafish was non-evaluable under the frozen endpoint. The current evidence therefore supports dataset-dependent, rather than universal, predictive value.

The task throughout: predicting whether edgeR agrees with a borderline DESeq2 significance call (adjusted p-value between 0.01 and 0.10), using a logistic regression whose regularization strength was selected by cross-validation on the training dataset alone, then evaluated once on a held-out dataset, never re-run or adjusted after seeing a result. On airway/pasilla, adding rank_stability moved PR-AUC from 0.50 to 0.65. On Bottomly, a valid external dataset with 1,997 borderline genes, the same unmodified design moved PR-AUC from 0.9491 down to 0.9230. Neither result overturns the other; both came from the same frozen design applied to different data, which is what makes the comparison meaningful.

What this is not: proven biological replication prediction, on any dataset. It's a cross-method agreement result (does a second DE tool agree with a borderline call from the first). The long-term aim, estimating whether a discovery-dataset finding replicates in an independent dataset, needs paired discovery/replication data this project doesn't have yet. This research phase is now closed; no further experiments are planned against this frozen design.

Why this exists

Built by Nezih Can Dikme, a high-school student learning how easy it is to be confidently wrong.

Before DEConcord, RNA-seq made sense in the dangerously comfortable summary-version: count reads per gene, compare two conditions, find changed genes. That explanation is technically related to reality, but it skips nearly everything capable of ruining an analysis.

Building the pipeline forced a confrontation with the missing layers: what makes a count matrix valid, why library size matters, why a difference of means only becomes a fold change on the right scale, why testing thousands of genes at once requires correction, and why statistical significance isn't the same thing as biological importance.

"It turns out there are more ways to produce convincing-looking nonsense from a count matrix than most explanations let on."

So DEConcord is currently focused on making those failure modes loud, testable, and difficult to ignore, one function, one broken test, and one increasingly specific error message at a time.

Every decision behind the code, what shipped, what broke, what got rejected, is written down in DEVLOG.md.
